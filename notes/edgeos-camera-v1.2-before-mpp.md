# 29 接入摄像头应用

让 EdgeOS 桌面里的 Camera 显示真实摄像头画面，并把拍摄的照片保存到板端数据分区。本章沿用前面的 AI Agent、SDK 与设备连接环境，不重复配置工具。

学习顺序是：**确认节点能采集 → 对照 SDK 接入 ISP → 加入桌面页面 → 部署并验证照片和资源释放**。看到 `/dev/video0` 或出现 Camera 图标，都不能单独作为适配成功的依据。

![Camera 实机预览与拍照成功提示](./images/edgeos-camera-photo.png)

*截图来自正式部署的 `v1.2.0-camera`，画面来自板载摄像头，不是设计稿；画面方向反映本次镜头安装方向。*

## 1. 确认摄像头是否可用

先让 Agent 做只读检查，再进行短时间采集。不要同时启动多个相机程序，也不要为检查摄像头去重新烧录固件。

~~~text
请通过 LYNX 核对当前 V853 的设备身份和空闲状态，检查 /dev/video*、
media/subdev、传感器名称、启动日志以及是否已有进程占用摄像头。
节点存在后，继续验证格式协商、申请缓冲区和连续取帧，不能只执行 ls。
不要重启或烧录，不启动会接管 LCD 的多媒体显示示例。
若 LYNX 命令接口异常，说明错误和实际使用的备用通道。
~~~

本次板端检查结果如下：

| 检查项 | 实际结果 | 如何理解 |
| --- | --- | --- |
| 视频节点 | 存在 `/dev/video0`、`video4`、`video8`、`video12` | VIN 通道不等于四颗摄像头 |
| 传感器 | 首路识别为 `gc2053_mipi` | 本章使用这一路 |
| 连续采集 | `/dev/video0` 完成 120 帧采集并导出原始图像 | 已超过“节点存在”的验证层级 |
| 第二路探测 | 日志中 `gc2053_mipi_2` 探测失败 | 不能据此否定首路；第二路未通过验收 |
| 其他视频节点 | 未逐一进行完整采集验收 | 不标记为全部可用；ISP 还会内部使用 `video12` |

**本次连接说明：** LYNX 状态接口确认设备序列号为 `20080411`、设备在线且没有冲突任务，但 `lynx_adb_shell` 调用超时。实际板端命令、文件传输和截图使用 Windows 主机 ADB，固定指定同一序列号；VM 中的代码检查和编译通过 SSH 完成。这不代表 LYNX Shell 已修复。

## 2. 对照 SDK 选择采集链路

SDK 根目录为 `~/100ask-course/sdk/tina-v853-100ask`，主要参考代码位于：

`external/eyesee-mpp/middleware/sun8iw21/sample/`

| 参考代码 | 重点阅读 | 本章如何使用 |
| --- | --- | --- |
| `sample_virvi/sample_virvi.c` | `AW_MPI_VI_GetFrame()` 与 `AW_MPI_VI_ReleaseFrame()` | 学习取帧、处理与归还缓冲区的配对关系 |
| `sample_virvi2vo/sample_virvi2vo.c` | VI 属性、`AW_MPI_ISP_Run()`、通道启停 | 参考格式与 ISP 生命周期；不运行它的 VO 显示链路 |
| `sample_takePicture/` | 拍照与编码流程 | 后续接入 JPEG 的参考；当前版本没有接入该编码链路 |
| `media/LIBRARY/libisp/isp_test.c` | `media_dev_init()`、`isp_init()`、`isp_run()` 及退出流程 | 本章 ISP 辅助程序实际调用的 SDK 接口 |

最后一项路径位于同一 `sun8iw21` 目录下，不在 `sample` 子目录内。

### 为什么不直接启动 sample_virvi2vo？

桌面已经由 LVGL 管理 framebuffer。带 VO 的示例会自行创建显示通道，直接照搬可能覆盖桌面或影响 LCD 状态。本章保留 LVGL 显示与触摸，只把采集图像送给 Camera 页面。

当前实现采用 **V4L2 采集 + SDK libISP + LVGL 预览**，并非已经移植了完整的 `AW_MPI_VI/VO/VENC` 应用：

~~~text
gc2053_mipi → sunxi-vin /dev/video0 → NV21 帧 → 像素转换 → LVGL 预览
                      ↑                           └→ 用户拍照 → BMP 文件
                SDK libISP 辅助进程
~~~

使用 MMAP 缓冲区取帧后，必须归还给驱动；退出时停止 ISP、停止视频流、解除映射并关闭设备。预览与拍照不在 LVGL 点击回调里阻塞执行，后台线程也不直接操作 LVGL 对象。

~~~text
请参考 SDK 的 sample_virvi、sample_virvi2vo 和 libisp/isp_test.c，
将摄像头接入现有 EdgeOS 桌面。显示仍交给 LVGL，不接管 VO 或关闭 LCD。
实现实时预览、拍照保存、错误提示、重试和返回时释放资源。
明确列出实际使用的接口，不把仅阅读过的 AW_MPI 示例写成已集成的功能。
~~~

## 3. 处理这份 SDK 的格式差异

驱动位于：

`lichee/linux-4.9/drivers/media/platform/sunxi-vin/vin-video/vin_video.c`

本次实操遇到两个容易导致“节点正常、应用却打不开”的问题。适配应限定在已确认的 `sunxi-vin` 驱动及格式上，不要放宽所有摄像头的检查。

### 能力标志不完整

`VIDIOC_QUERYCAP` 返回的 `device_caps` 没有完整填写采集能力，而 `capabilities` 中存在对应标志。若完全按通用逻辑优先采用 `device_caps`，会误判为不支持多平面采集。

当前后端核对驱动名称后，才为这份 SDK 回退检查 `capabilities`。其他驱动仍使用正常规则。

### bytesperline 不能直接当成亮度平面的步长

首次探测时部分格式元数据为零；申请缓冲区并重新打开后，驱动又返回了非零值。检查源码可见，它按 `width × depth / 8` 填写 `bytesperline`，对于本次 NV21 布局，该值不是 Y 平面每行的字节数。

因此，当前后端同时验证协商的像素格式、平面数、图像尺寸、MMAP 长度和每帧有效数据长度，只接受已实测的连续 NV21 布局。未知布局明确报错，不能因为要“出图”就忽略边界检查。内核驱动本次没有修改。

### 能取帧，还要检查 ISP

未启动 ISP 时，导出的真实图像出现明显偏绿；接入 SDK ISP 后有所改善。ISP 初始化失败时页面应提示错误，不能悄悄使用失真的画面冒充正常预览。

SDK ISP 的日志还包含传感器温度读取告警；本次没有阻止出帧。正常退出时库会将 ISP 上下文保存到 `/mnt/extsd/` 下的 `isp0_*_gc2053_mipi_ctx_saved.bin`。这是 SDK 库的实际行为，不是照片目录，也不能把它写成完全没有磁盘写入。

## 4. 加入桌面与照片保存

修改位置仍是 `~/Downloads/edgeos/v853-port/`，原始 EdgeOS 源码目录保持不变。

| 文件 | 负责什么 |
| --- | --- |
| `main.c` | 新增 Camera 图标、路由和退出清理 |
| `camera_ui.h` | 预览区域、状态、拍照按钮、重试与返回 |
| `camera_backend.h` | V4L2 缓冲区、后台取帧、格式检查、像素转换和 BMP 保存 |
| `camera-isp.c` | 调用 SDK libISP；通过就绪信号通知桌面 |
| `settings_ui.h` | 相机使用期间不触发自动调暗，保留其他设置功能 |
| SDK `package/gui/v853-edgeos-desktop/` | 打包桌面与 ISP 辅助程序，并加入源文件依赖 |

页面按当前显示尺寸计算预览区域，保持相机画面比例，多余空间留边。采集尺寸与屏幕尺寸分开管理，不因为更换横屏或竖屏就强行拉伸相机画面。

本版只在进入 Camera 后打开设备。点击 **Take photo** 才保存照片；进入页面不会自动拍照。文件使用唯一时间戳命名，保存到：

`/mnt/UDISK/edgeos-camera/photos/`

照片格式为 BMP，不依赖尚未接入的 JPEG 编码器。保存前检查数据分区确实已挂载且空间充足，保存失败则显示错误；不能把未挂载的数据目录当成根分区目录继续写。照片时间戳来自板端时钟，不等于已经校准过真实时间。

## 5. 编译与部署

~~~text
请在 VM 的 Tina SDK 中交叉编译 v853-edgeos-desktop 软件包，
同时构建桌面和 edgeos-camera-isp。核对目标架构、构建日志和文件哈希。
部署前备份现有桌面，确认剩余空间和数据分区挂载状态。
先传输到暂存位置，校验后停止旧服务并替换，再启动正式服务。
本次只更新应用，不重新烧录固件；最后确认运行中的程序确实是新版本。
~~~

本次根分区的剩余空间不足以额外容纳 ISP 辅助程序，因此板端增量部署采用：

- 桌面程序：`/usr/bin/edgeos-v853`。
- ISP 实体文件：`/mnt/UDISK/edgeos-camera/bin/edgeos-camera-isp`。
- 固定入口：`/usr/bin/edgeos-camera-isp`，符号链接到上述实体文件。
- 旧桌面备份：`/mnt/UDISK/edgeos-camera/backup/edgeos-settings-style`，Windows 端另有一份。

SDK 软件包仍把 ISP 实体文件安装到 `/usr/bin`，以便后续制作完整固件；这与本次为节省 overlay 空间采用的增量部署不同。**本章没有重新生成并烧录完整固件，也没有完成断电启动验收。**

辅助进程有一小时的单次运行保护上限，到期后需要重新进入相机。返回桌面会主动停止它，不应留下常驻 ISP 进程。

## 6. 验证画面、照片与退出

~~~text
请从正式桌面打开 Camera，确认画面连续更新，而不是只显示第一帧。
点击拍照，检查保存成功提示、文件大小，并传回主机打开验证。
然后返回桌面，确认摄像头文件描述符和 ISP 进程已释放。
反复进入与退出，检查进程、内存和设备占用；再回归 Settings 和 Drawing。
保留真实 framebuffer 截图、采集日志及照片，不用设计稿代替实机证据。
~~~

验证时需要区分三种证据：节点和驱动日志说明设备被注册，连续取帧说明采集链路可用，而实机预览、成功打开的照片及退出后的资源检查才说明应用链路接通。

### 本次已取得的证据

实时预览中应用帧计数从 144 增加到 555，画面随现场变化。此计数由成功出队的帧累计，不能改用本 SDK 一直返回零的驱动 `sequence` 字段。采集请求为每秒 30 帧，当前每三帧转换一次供 UI 使用；这不是已经做过性能基准测试的承诺。

点击拍照后生成 `photo-1245-989534423.bmp`，文件为 **921,654 字节**。传回 Windows 后确认是可解码的 RGB BMP，板端和主机 MD5 一致：`c2ffdf195b0224649f618f75b7c007a0`。文件名中的时间很小，是因为本次板端系统时钟尚未校准，而非照片保存异常。

![从板端传回并解码的实际照片](./images/edgeos-camera-saved.png)

返回桌面后，`/proc/<桌面PID>/fd` 不再有 `/dev/video0`，应用线程数从 2 回到 1；ISP 日志出现 `STOPPED`，辅助进程退出。保留桌面自身的显示、触摸描述符是正常的，不应为了“清理相机”把它们一起关闭。

另外完成了以下回归检查：

| 项目 | 结果 |
| --- | --- |
| 反复进入、退出相机 10 轮 | 全部通过；桌面 PID 不变，无残留视频描述符或 ISP 进程 |
| 每轮退出后的资源 | 线程数为 1，VmRSS 为 1,696 KiB；这是短循环结果，不替代长时间稳定性测试 |
| 主动中止本应用的 ISP 辅助进程 | 页面显示 Stopped 和错误，禁用拍照；点击 Retry 后重新预览 |
| 主机横向、竖向布局 | 各 5 轮；检查缺失设备反馈、按钮边界和退出清理，使用合成图案，不作为实机截图 |
| 原有设置首页 | 正常显示并读取状态，未改变网络与亮度配置 |
| Drawing | 修正大画布分配后，实机画布显示、落笔与返回通过 |

本次触摸验证通过 evdev 注入完成，不等同于全面的物理手指操作验收。

回归时还发现原有 Drawing 将整块画布分配到仅 64 KiB 的 LVGL 内置池，导致申请失败。本次将画布像素改为独立分配，并在退出时释放；没有修改公共 `lv_conf.h`。主机测试补充了相机与绘图的切换检查，避免只验证新应用而忽略原有功能。

## 常见问题

| 现象 | 优先检查 |
| --- | --- |
| 有节点但页面报不支持 | QUERYCAP 的能力字段、协商格式与当前 SDK 的元数据差异 |
| 有帧但颜色异常 | NV21 的 V/U 顺序、步长、ISP 是否正常启动；不要先修改 UI 配色 |
| 黑屏或取帧超时 | 传感器连接、设备占用、ISP 日志、STREAMON 与缓冲区状态 |
| 预览正常但保存失败 | `/mnt/UDISK` 挂载、空间、写权限及完整写入结果 |
| 返回后再次打开失败 | ISP 子进程、STREAMOFF、MMAP 和设备描述符是否释放 |
| 相机覆盖整个桌面 | 是否误用了示例中的 VO 显示链路 |

完成这一章的标准是：**Camera 使用真实画面，照片可以打开，失败有反馈，返回后资源能释放，原有桌面和设置仍可使用。**
